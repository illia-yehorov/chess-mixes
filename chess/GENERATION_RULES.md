# Правила генерации шахматной солянки

## 1. Источник данных и фильтрация

- Общий `generate_mix.py` читает локальную сжатую базу Lichess (`source` в конфигурации `configs/*.toml`). Сама большая база не хранится в Git.
- Пропускаются записи без нужных столбцов и с некорректными значениями рейтинга, популярности или числа прохождений. Границы рейтинга `rating.min`–`rating.max` включены; применяются `popularity_min` и `min_plays`.
- Количество ходов решающей стороны равно половине числа полуходов в решении Lichess. Записи с нечётным числом полуходов исключаются. Учитываются только ходы из диапазона `moves.min`–`moves.max` с положительными `move_weights`.
- ID задачи попадает в каждую указанную в TOML тему (`themes.id`), присутствующую в списке тем Lichess; один ID может одновременно подходить для нескольких тем. При выборе повтор этого ID не допускается.
- Python подсчитывает все подходящие ID, но перед созданием HTML отбирает не более `max_puzzles_per_theme` на каждую тему с учётом весов длины решения (подробнее в разделе 6). Сам порядок выдачи задач определяется при нажатии кнопки в браузере, а не заранее Python-скриптом.

## 2. Независимые веса тем

1. Сначала для позиции определяется требуемое количество ходов по квоте из раздела 3.
2. Только среди тем с доступными задачами этого количества ходов тема выбирается случайно пропорционально её `themes.weight`. Больший размер базы задач в теме сам по себе не увеличивает её вес.
3. Из выбранной группы «тема + количество ходов» один неиспользованный ID выбирается равновероятно.
4. Нулевой вес отключает тему или количество ходов. Количество ходов без задач в какой-либо теме с положительным весом исключается. Веса тем **не влияют** на квоты количества ходов.

## 3. Сбалансированные квоты по количеству ходов

- На каждое нажатие сначала рассчитывается целочисленная квота: сколько задач каждого количества ходов должно появиться. Это заменяет прежнюю независимую случайную жеребьёвку типа хода для каждой задачи.
- Используется накопительный метод наибольшего отставания. Для каждого очередного места вычисляется идеальная накопленная доля `(всего мест + 1) × вес хода / сумма активных весов` и вычитается уже выделенное число мест этого вида. Место получает вид с максимальным отставанием. При равенстве выбор случайный.
- Затем все квотированные количества ходов перемешиваются методом Fisher–Yates. Порядок непредсказуем: нет строгого правила «каждая четвёртая — четырёхходовка». Для полученного количества ходов отдельно выбираются тема и конкретная задача.
- Пример: при весах `3 хода = 15`, `4 хода = 5` и `puzzles_per_click = 10` в первой десятке будут `7+3` либо `8+2`; во второй — дополняющие количества. **За 20 успешно выбранных задач выходит ровно 15 трёхходовок и 5 четырёхходовок.** Обе десятки независимо перемешаны.
- Фактические количества сохраняются между нажатиями и после перезагрузки страницы в `localStorage`: `usedPuzzles:<имя-конфига>:moveBalance`. При изменении доступных видов ходов или их весов квоты начинают отсчёт заново, не удаляя историю использованных ID. Состояния разных конфигураций разделены.
- Если активно только одно количество ходов, все задачи имеют его. Для произвольных весов округление происходит с учётом предыдущих выдач, чтобы не накапливать перекос от округления каждой десятки отдельно.

## 4. Повторы и исчерпание задач

- Использованные ID хранятся в `localStorage` под ключом `usedPuzzles:<имя-конфига>` и исключаются независимо от числа тем, к которым относятся.
- Если задачи требуемой длины закончились в истории неиспользованных, начинается новый цикл использованных ID. Задача, уже выбранная **в текущем нажатии**, при этом повторно не выбирается.
- Если доступных уникальных ID для запланированной квоты недостаточно даже после сброса истории, выводится предупреждение и открываются только выбранные задачи. Недостающая четырёхходовка не заменяется молча трёхходовкой. В накопительном балансе учитываются только реально выбранные задачи.
- Кнопка пытается открыть до `puzzles_per_click` вкладок `https://lichess.org/training/<ID>`. Браузер может блокировать массовое открытие вкладок.
- Под кнопкой показываются ID **последней выданной подборки в порядке вкладок** со ссылками на конкретные задачи Lichess. Список сохраняется в `localStorage` с ключом `usedPuzzles:<имя-конфига>:lastSelection:<заголовок HTML>`, отображается после перезагрузки и обновляется при следующем нажатии. При заблокированных вкладках ID всё равно доступны для ручного открытия. Это диагностика выбора, а не проверка фактической страницы Lichess.
- При генерации рейтинг фильтруется по локальному CSV. При выдаче задач дополнительно выполняется браузерная проверка по актуальному Lichess API (раздел 5).
- Ранее сгенерированные HTML не меняются автоматически: для перехода на новые правила нужно повторно запустить генератор из обновлённой версии проекта.

## 5. Проверка актуальности выданных задач

- При генерации Python сохраняет в HTML компактные исходные данные **по каждому уникальному отобранному ID**: рейтинг, ID исходной партии (из `GameUrl`, если доступен), начальный ход соперника и последовательность ходов решения. Эти сведения относятся к **локальной версии CSV на дату генерации**, а не ко всем будущим обновлениям базы.
- После нажатия кнопки выдачи HTML **сразу открывает вкладки** с `https://lichess.org/training/<ID>`, затем **автоматически и последовательно** запрашивает только выданные ID через публичный `GET https://lichess.org/api/puzzle/<ID>`. Нельзя сначала ожидать сетевые запросы и лишь потом открыть вкладки: браузер может заблокировать их как всплывающие окна без непосредственного клика пользователя. Поэтому проверка диагностическая, не блокирует вкладки и не подменяет задачи автоматически.
- Для каждого ID сравниваются: ID из ответа, исходная партия (если известна), начальный ход (если присутствует в ответе), **полное решение** (поле CSV `Moves` без первого хода соперника соответствует API `puzzle.solution`), наличие темы, фактически выбранной генератором, и текущий рейтинг **в рамках настроенного диапазона**. Длина решения проверяется через точное совпадение ходов. Если рейтинг изменился, но всё ещё входит в диапазон, задача считается подходящей, а изменение отображается отдельно.
- **Особенность темы `mate`:** Lichess намеренно исключает общий тег `mate` из JSON API (`JsonView.simplifyThemes`), хотя он присутствует в CSV. Поэтому для выбранной темы `mate` считаем её подтверждённой, если API вернул `mate` или один из `mateIn1`–`mateIn5`. Если нет ни одного из этих тегов, проверка сообщает о несоответствии. Для других тем, включая `backRankMate`, требуется точное совпадение; только наличие `backRankMate` не заменяет `mateInN`.
- Статусы выводятся под ID последней подборки: **подходит**, **не подходит** (например, рейтинг вышел за границы, изменилась тема или решение, API ответил HTTP 404) либо **не удалось проверить** (ошибка сети, CORS, некорректный ответ, временная ошибка API). Сетевая ошибка **не означает**, что задача удалена. Если Lichess возвращает HTTP 429, проверка текущей подборки прекращается, а следующие запросы блокируются минимум на минуту.
- Согласно опубликованной спецификации Lichess, публичный endpoint не требует токена и предусматривает `Access-Control-Allow-Origin: *`, поэтому его можно вызывать из GitHub Pages напрямую. Фактическая доступность всё же зависит от сети, сервера и политики браузера. Запросы выполняются **строго по одному**, как рекомендует Lichess.
- Проверяются **только ID, выданные текущим нажатием**, а не вся база. После обновления страницы последние ID остаются видимыми, но статус проверки заново не восстанавливается; он зависит от текущих данных API. Предыдущие автономные HTML не получают эту функцию автоматически: их нужно повторно сгенерировать из CSV с обновлённым шаблоном и затем опубликовать.
- Проверка подтверждает ответ API на момент запроса; она **не может доказать**, какую страницу Lichess реально отрисовал в новой вкладке после перенаправлений, и не гарантирует неизменность задачи в будущем. Для полного обновления набора следует перегенерировать HTML на свежем CSV.


## 6. Ограничение количества задач и приоритет качества

- `max_puzzles_per_theme` — максимальное количество задач **для каждой темы**, по умолчанию **1000** из `configs/0-defaults.toml`. Индивидуальный TOML может переопределить параметр. Значение `0` отключает ограничение задач, отрицательные и нецелые значения недопустимы.
- Генератор применяет старые ограничения рейтинга, `popularity_min`, `min_plays`, тем и длины решения до отбора лучших. Столбец `RatingDeviation` теперь также должен содержать корректное неотрицательное число.
- Приоритет качества — сначала **выше Popularity**, при равенстве **ниже RatingDeviation**, затем **больше NbPlays**, при полном равенстве — лексикографический ID. Достаточное количество прохождений по-прежнему гарантируется `min_plays`; дополнительные произвольные пороги не вводятся.
- При чтении CSV генератор считает все совпадения и поддерживает ограниченные по размеру кучи лучших кандидатов по каждой паре «тема + число ходов». В памяти не приходится хранить все найденные задачи, если лимит включён. Результат воспроизводим для одинаковой базы и конфига.
- После прохода по базе лимит **на тему** распределяется по положительным `move_weights`, нормализованным внутри настроенного диапазона ходов. Округление производится методом наибольших остатков. Например, 1000 задач с весами 2 хода = 20, 3 хода = 50, 4 хода = 30 превращаются в квоты **200, 500, 300**.
- Если по одному количеству ходов недостаточно подходящих задач, недобор перераспределяется **пропорционально весам остальных ходов** с доступными кандидатами, пока не достигнут лимит на тему либо все подходящие задачи не исчерпаны. Например, при наличии только 100 двухходовок их квота не создаёт пустые ID, а недостающие 100 мест распределяются между 3 и 4 ходами.
- Отбор по каждой теме производится независимо; один и тот же ID может присутствовать в нескольких темах и занимает слот в каждой из них. В браузере его повтор всё равно блокируется глобальной историей ID. Веса тем влияют только на **выдачу** задач, а не на лимит.
- Только выбранные ID и соответствующие данные для API-проверки сохраняются в HTML. При каждом запуске консоль показывает для каждой темы общее число **найденных** и **отобранных** задач, а также такие же числа **отдельно для 2, 3, 4 и других активных длин**.
- Эти квоты ограничивают состав подготовленного HTML и **не заменяют** квоты при каждом нажатии кнопки, описанные в разделе 3. Выдача из выбранного набора по-прежнему случайная, с учётом весов ходов и истории повторов.
- `chess-generate.bat` **без аргументов** обходит номерные TOML-файлы в `chess/configs/` в порядке имён, пропуская `0-defaults.toml`, генерирует каждый последовательно и прекращает работу при ошибке. Значение `0` не используется как аргумент батника. Обычные `chess-generate.bat 1`–`4` работают без изменений.


## 7. Общие настройки конфигураций

- `chess/configs/0-defaults.toml` — **общий конфиг, не генерация отдельного микса**. В него вынесены общие значения `name` (на случай будущих миксов), `source`, `template`, `puzzles_per_click`, `max_puzzles_per_theme = 1000`, `popularity_min`, `min_plays`, диапазоны рейтинга и ходов, `move_weights`, `page.heading`. Общий `name` переопределён в каждом существующем миксе.
- При запуске любого микса Python сначала читает `0-defaults.toml`, затем TOML нужного микса. Простой ключ переопределяется целиком. Вложенные таблицы (`rating`, `moves`, `move_weights`, `page` и др.) объединяются рекурсивно по полям, а отдельные значения из микса имеют приоритет. Поэтому можно изменить только `rating.min`, сохраняя унаследованный `rating.max`.
- Массивы (включая `[[themes]]`) заменяются **целиком**, без частичного объединения; темы, `output.filename` и `page.title` у каждого микса собственные.
- Нулевой вес хода отключает этот ход даже при положительном значении в общих настройках. Унаследованные веса других ходов при этом сохраняются. `moves.min`/`moves.max` определяют актуальные значения независимо от того, какие дополнительные ключи лежат в `move_weights`.
- Файл `0-defaults.toml` не имеет `[[themes]]` и `output.filename`; явная попытка сгенерировать HTML из него отклоняется с понятной ошибкой.
- `chess-generate.bat` без аргументов выбирает **только миксы**, игнорируя `0-defaults.toml`. Для запуска по отдельности используются номера 1–4. Аргумент `0` не используется.
- Изменение настроек в общем файле влияет на **следующую** генерацию всех миксов, если параметры не переопределены индивидуально. Уже созданные HTML-файлы не меняются.
